# Argus — Project Brief & Decisions

> Watch and steer your Claude Code agents live, from the terminal, on any machine.
> This brief captures the design session of November 14, 2026. Read it first
> whenever work resumes in a new session.

## Vision

The "AI agents at work" visuals going viral on X are either cartoons (pixel offices)
or bare metrics (htop-style). Argus combines both worlds: a classic terminal aesthetic,
complete metrics, **and a live, visual view of how agents hand off tasks and message
each other**. It brings agents running on different machines into a single screen.

## Decisions

| Topic | Decision |
|---|---|
| Name | **Argus** (the hundred-eyed watchman). `argus` and `argus-cli` are taken on crates.io → package name `argus-tui`, binary name `argus` |
| Target agent | Claude Code (Codex and others later via adapters) |
| Language | Rust + ratatui + crossterm |
| Platforms | macOS (Intel + Apple Silicon), Linux, Windows — single static binary |
| UI language | Multilingual; English (default) + Turkish in the first release (`locales/*.ftl`, Fluent). Detected from the system, overridable with `--lang` |
| Repo language | Everything on GitHub is in English: README, docs, code comments, commits, issues, PRs |
| License | MIT |
| Repository | `argus` on the maintainer's personal GitHub account |
| Standalone | Argus always works on the local machine alone — no hub, SSH or network required. Remote hosts are an optional extra |
| Distribution | GitHub Releases (5 targets) + Homebrew tap and Scoop bucket served from this repo (`Formula/`, `bucket/`), regenerated by the Release workflow. Releases are automatic (maintainer's choice): a version bump on `main` with green CI publishes a pre-release (`autorelease.yml`). winget needs a one-time submission to microsoft/winget-pkgs by the maintainer; reserved id `SerkanKoyun.Argus` (the bare name `argus` is taken by unrelated packages) |
| Teams view | Cards (the tree was tried and rejected as plain text): coordinator box on top, one wide card per busy team with a roles line (the team's usual roles from `team_roles` or today's, and which are at work now) and each agent's name, task and plain-word activity; finished teams on one line. `esc` from any view leaves a chosen team. Starts there when teams or a coordinator are known. Graph nodes also show the task |
| Network view | With a coordinator or team labels it shows the hierarchy: coordinators on top, a cluster per team (label as title), leads above the agents they started; `g` switches to host bands. Unknown ids are named from their task message |
| Nesting | Coordinator → team lead → the lead's agents. Parents come from spawn results (agentId), not from the file layout (all subagents of a session are stored flat); unnamed agents are named from `<name> · <run> · <task>` descriptions; teams are inherited from the parent |
| Focus | Views show live agents only: finished agents move to the History view (`H`, `f` toggles). `s` / Fleet+Enter scope every view to one host, `t` opens Teams, Enter scopes every view to one team (`T` cycles); both combine |
| Runs | A run is read from `runs/<run-id>/` (`run.json`, stage files with front matter and a decision line) and from agents whose description names the run id. Files are often left `pending`, so live agents are the main signal; a `pending` file is a template and its text is never a decision; the last decision in a file counts (rounds are appended). Agent type → stage via `run.json` `stages[].agent`. Leads (agents that started others for the run) are not stage workers |
| Backlog view | `b` opens a queue of work rather than agents: "Waiting on you" first (what the user can act on), then per owner NOW → QUEUED → WAITING, then the unassigned pool. Built by one pure function (`queue::build`) from the snapshot, so no queue concept enters the wire protocol and the team/host filters come free. Every item is descriptive (title, reason, age, source, owner; detail panel with description, context, path, blockers) and carries the chain of what it waits on to its root; approvals show how many items they hold. Runs queue only their next pending stage (later ones wait on it in turn) |
| Backlog sources | Agent Teams tasks keep their description, active form, file and date; `run.json` stages keep their planned agent type; `tasks/todo.md` next to the sessions is parsed leniently (open boxes, indented descriptions, "waiting on you" headings, wait markers) with caps (1 MiB, 200 per file, 500 total, 30 days). Only todo data is new in the snapshot (`todos`, additive; protocol stays 1) |
| Remote todo.md | tasks/todo.md is read locally by default (`--no-todos` turns it off); remote collectors send it only with `--remote-todos` (`argus collect --todos`), and frames that carry it unasked are dropped, because titles may hold personal data |
| Model label | Lists show a short model (`claude-opus-5-5` → `opus-5.5`, date suffix and `[1m]` dropped, `?` when unknown) from one helper (`short_model` in `src/ui/common.rs`). Overview shows MODEL only while agent names keep 10 columns and hides HOST with a single host; Room cards add it to the host title only when it fits |
| Claude account | Each `Host` carries an optional `account` (organization, plan, masked email) read from `oauthAccount` in `.claude.json` (`<claude dir>/.claude.json`, then `~/.claude.json`), checked at most once a minute and parsed only on change. The email is personal data: it is masked at the source (`s***@example.com`) so the raw address never enters a snapshot, `argus snapshot`, logs or SSH; tokens and other fields are never deserialized; the remote side masks again on arrival. Shown by default (the maintainer asked for it) and turned off with `--no-account`, which also reaches remote collectors (`argus collect --no-account`) and `:connect` hosts. Additive field, protocol stays 1 |
| Aesthetic | Dark theme, monospace, ratatui bordered panes, braille lines, no cartoons |

## Screens (10)

Design mockups (private canvas, owner only): https://claude.ai/artifact/7QZw7PkMj3kAiQHbydCgU5

1. **Overview** — hosts (with their Claude account), agent tree (model, state, tool, tokens, context, cost), flow summary, metrics, event log
2. **Sequence** — agents as lanes, messages as arrows; task board; selected message details
3. **Agent detail** — context breakdown, tokens/cache/cost, throughput, tool calls, files touched, live transcript
4. **Fleet** — collector status, RTT, clock skew, Claude account (masked), alerts, topology, cost per host
5. **Live graph** — nodes and edges, messages travel along edges, edge width = traffic
6. **Agent room** — a "now" line on every agent, a bubble for the request it is sending, open requests with wait times
7. **Live lanes** — time flows right to left, vertical arrows between agents, "who asks whom for what" matrix
8. **Channel** — IRC/weechat-style live chat with action and approval lines, member list
9. **Task map** — the work, not the agents: one row per orchestrator run (`runs/<run-id>/`)
   with stage chips Analysis → Plan → Development → Test → QA → Security → CI → Merge, who
   has the current stage, and a bottleneck panel (longest stages, rework loops, blocked).
   Falls back to task dependencies and the critical path when there are no runs
10. **Pair view** — two agents' terminals side by side with the message channel between them

Also: **Teams** (`t`), **History** (`H`) and **Backlog** (`b`) — queued and waiting work per
agent with the reason and root of each wait, what waits on the user, and the unassigned pool
from `tasks/todo.md`.

Switching: `1`–`0`, `tab`, `:view <name>`. The selected agent and time cursor carry over between views.
Agent messages and "now" descriptions are shown in the user's language.

## Architecture

```
[Machine X: Claude Code] ── collector ──┐
[Machine Y: Claude Code] ── collector ──┼──▶ argus (TUI, your terminal)
[Local machine]          ── collector ──┘        (optional: central hub)
```

- **Collector:** a mode of the same `argus` binary. Reads `~/.claude` (session JSONL, teams/inboxes,
  tasks), the process table and optional hook events; normalizes them into one event schema.
- **Connecting:** `:connect X` → reuses the user's SSH, finds argus on the remote (PATH, `~/.cache/argus`,
  `~/.local/bin`, `~/.cargo/bin`, `/usr/local/bin`, Homebrew), copies itself when OS/CPU match,
  otherwise the remote downloads its own build from GitHub releases (Windows → Linux works); starts the collector,
  streams over the SSH channel. No open ports, no VPN. Nothing is left running on disconnect
  (optional persistent service mode). Without SSH (e.g. Windows) the collector dials out over TLS.
- **Hub (optional):** for team-wide monitoring and continuous recording.
- **Platform-independent commands:** the TUI sends structured commands and the collector executes
  them locally (no shell-quoting issues across bash/PowerShell).

## Driving agents

- New work: `> prod-1 ~/repo: update the README` → collector runs `claude -p ... --output-format stream-json`
- Instructions to a running agent: via `--resume` / Agent SDK if Argus started it; tmux or the teams inbox otherwise (fragile)
- Approvals: routed to the TUI via hooks / `--permission-prompt-tool`; `a` approve, `r` reject
- Exact states: transcripts are silent during long tool calls, so `argus hook --install` also
  records lifecycle events in an open JSONL format (`docs/EVENTS.md`). Other orchestrators
  report through the same format (`ARGUS_EVENTS`); agent-orchestra's log is read as is.
  No orchestrator-specific code. A subagent that ended its turn without handing back while
  agents it started still run is waiting for them, not finished. Subagents of the same type are named by their task
  description; without a team filter the Overview flow tags each line with its team.
  Team sources, in order: Agent Teams, `team`/`agentName` in events, name rules in
  `<claude dir>/argus/teams.json` (strip role prefix, longest team code, aliases, labels),
  project folder. Without an Agent Teams task list, each subagent's assignment is a task.
  With team codes known, the coordinator label goes only to sessions that started agents
  of those teams (or independent reviewers), not to every session that started a helper.
  `argus init` infers those rules (roles = shared first segments, team = longest prefix
  shared by two different jobs) so users do not have to write them
- Recommendation: let Argus launch agents whenever possible
- Limitation: interactive menu commands (`/config` etc.) are not supported

## Platform notes

- Windows: OpenSSH server is off by default; Claude Code may run natively or inside WSL — scan both; no tmux
- Legacy `cmd` renders braille/colors poorly; Windows Terminal is fine; color depth is detected
- CI: GitHub Actions matrix on Windows + macOS + Linux; tagged releases built automatically (cargo-dist)
- README GIFs generated automatically with `vhs`

## Status (Nov 18, 2026)

All ten numbered views plus Teams, History and Backlog are implemented and recorded from the demo in
`docs/media/`. Live collector, SSH remotes (auto-install, replaced when its version differs), command bar, headless runs,
`--resume` messages, the PermissionRequest approval hook and lifecycle events are done and covered by
end-to-end tests in CI (fixtures, SSH loopback, hook round trip).

v0.1.1 is published (pre-release) with binaries, Homebrew and Scoop packages; it adds
cross-platform remote installs (Windows → Linux), mouse/F-key view switching and Windows
rendering fixes found while the maintainer tested on Windows.

v0.1.33 adds the Backlog view (`b`): Agent Teams tasks, run stages, open requests and
`tasks/todo.md` as one queue with waiting chains; todo files stay local unless
`--remote-todos` is given.

v0.1.34 shows a short model label in the agent lists and each machine's Claude account
(organization, plan, masked email) in Fleet and Overview; `--no-account` turns it off.

Next: replay/scrubbing of past sessions, per-team budgets and metrics, winget, config file for hosts,
richer Agent Teams support (task files, teammate names) once verified on real data.
